Analytics Pipeline Overview

How a click becomes an analytics data point.

GET /:slug → LinksController#link ↓ after_action :track_visit (fires on every successful response) ↓ RecordVisitJob.perform_later (Solid Queue → separate SQLite) Captures: link_id, ip_address, user_agent, referer, timestamp Computes: VisitorHash.compute(ip, ua, link_id, timestamp) ↓ Visit row created (processed_at: nil) ↓ ProcessVisitsJob (every 10s via recurring.yml) 1. Skip if GeoLite2-City.mmdb missing 2. CrawlerDetect → destroy if bot 3. MaxMindDB lookup → country, city, subdivision, lat/lng 4. DeviceDetector → device_type, browser_name, os_name 5. Set processed_at, invalidate chart cache ↓ VisitsController#index (cached 60 min per link per time range) → time-series, device breakdown, geo breakdown, world map

Key design choices

  • Server-side tracking only — visit is recorded in after_action, independent of whether the client's JS executes. No tracking pixel, no client-side beacon.
  • Deferred writes — the redirect hot path only enqueues to Solid Queue's SQLite; the primary DB writer lock stays free.
  • No cookies set on click — unique visitors estimated via visitor_hash instead.

Visitor Hash: The Uniqueness Model

How ugo counts "unique visitors" without cookies or persistent identifiers.

HMAC-SHA256( key = "ugo-visitor-hash:{UTC date}:{secret_key_base}", data = "{ip}|{user_agent}|{link_id}" ) → truncated to 32 hex chars (128 bits)

What works well

  • Daily salt rotation — hashes from day N cannot be correlated with day N+1. This is the Plausible/Fathom approach.
  • Link-scoped — link_id in the HMAC input means a visitor to Link A cannot be correlated with the same visitor on Link B. Cross-link profiling is impossible.
  • Server-secret keyed — an attacker with only the hash cannot brute-force the IP without secret_key_base.
  • Well-tested — the test suite covers determinism, daily rotation, IP/UA/link divergence, and nil handling.

Limitations & caveats

  • Same-day only — "unique visitors" is meaningful within a single day. Weekly/monthly uniques are overcounted since hashes rotate daily.
  • Shared IP conflation — users behind the same NAT with the same browser/OS appear as one visitor.
  • UA changes — browser updates mid-day produce a new hash for the same person.
  • VPN/proxy blind spot — VPN exit node IP + common UA = many distinct people collapsed into one hash.
VERDICT: Solid privacy design, but "unique visitors" should be understood as an estimate, not a precise count.

Privacy: What Data Is Stored

The visits table is the core privacy surface. Here is exactly what is persisted per click.

Stored in visits table

  • PII ip_address — raw, untruncated IP (NOT NULL)
  • PII user_agent — full UA string (NOT NULL)
  • META referer — referring URL
  • PSEUDO visitor_hash — daily-rotated pseudonym
  • GEO country, city, subdivision, country_code
  • GEO latitude, longitude, accuracy_radius
  • DEVICE device_type, browser_name, os_name
  • META timestamp, processed_at, link_id

Assessment

HIGH Raw IP is stored permanently alongside the visitor hash. The entire point of the daily-rotated hash is to avoid persistent identifiers, yet the raw IP — a directly identifying PII under GDPR Art. 4(1) — sits in the same row, indefinitely (until the cleanup job runs).

MED Lat/lng coordinates at city-level accuracy can narrow a person's location to a few km. This exceeds what most privacy-respecting analytics tools store.

INFO The privacy policy at /privacy honestly discloses IP and UA collection. However, it does not mention lat/lng storage.

VERDICT: The raw IP storage undermines the privacy guarantees the visitor hash was designed to provide.

Privacy: Recommended Remediations

1. Drop raw IP after processing

Once ProcessVisitsJob has performed the GeoIP lookup and computed the visitor hash, the raw IP has served its purpose. Null it out:

visit.update(processed_data.merge(ip_address: nil))

This requires making ip_address nullable in the schema. The visitor hash already captures uniqueness; geo data is already extracted.

2. Drop lat/lng or reduce precision

The analytics dashboard never displays lat/lng — it only uses country, subdivision, and city. Consider either not storing coordinates at all, or truncating to 1 decimal place (~11 km precision) if future features need them.

3. Truncate user_agent after parsing

After DeviceDetector extracts device_type/browser/OS, the raw UA string is no longer needed. Replace it with a normalized key like "mobile|chrome|android" or null it out.

4. Update privacy policy

Disclose lat/lng storage (or remove it). If IP is nullified post-processing, update the policy to say "IP addresses are used transiently for geolocation and discarded."

Security Findings

Issues found during the source audit, ordered by severity.

HIGH No Content Security Policy (CSP)

config/initializers/content_security_policy.rb is entirely commented out. Combined with the admin_scripts.html_safe injection in the layout, a compromised admin account can inject arbitrary JavaScript on every page for every user. Even without admin compromise, the lack of CSP means any XSS vector anywhere in the app has unrestricted access to the DOM, cookies, and external exfiltration endpoints.

HIGH admin_scripts renders unescaped HTML

In application.html.erb: AppConfig.shared.admin_scripts.html_safe. This is intentional (for injecting analytics snippets) but is a stored XSS vector. If an attacker gains site_admin access, they own every session. There is no validation, no allowlist, and no sandboxing. The admin settings form accepts arbitrary HTML/JS.

MED No rate limiting on redirect endpoint

GET /:slug has no rate limit. An attacker can trivially inflate a link's analytics by scripting requests. The SessionsController has a rate_limit (10 per 3 min) but the redirect hot path and the API have none. No Rack::Attack middleware is configured.

MED Permanent session cookies

cookies.signed.permanent[:session_id] creates a cookie that expires ~20 years from now. If a session token is stolen, it remains valid indefinitely (no server-side expiry mechanism found beyond manual session destruction).

Security Findings (cont.)

MED API authentication is timing-attack susceptible

Api::ApplicationController compares @api_key == AppConfig.shared.admin_api_key using Ruby's == which is not constant-time. The admin API key is the most privileged credential. Use ActiveSupport::SecurityUtils.secure_compare instead.

MED Host authorization disabled in production

config.hosts is commented out in production.rb. This leaves the app open to DNS rebinding attacks and host header injection, which can poison password reset links, cache keys, and canonical URLs.

LOW MissionControl::Jobs mounted without explicit auth guard

mount MissionControl::Jobs::Engine, at: "/jobs" — the route file does not wrap this in an authenticate block. If MissionControl does not enforce its own auth, the queue dashboard could be publicly accessible. Verify that it's gated or add a constraint.

LOW Layout meta tags contain stale placeholder content

application.html.erb sets lang="es", meta name="description" referencing "Cotizaciones y servicios personalizados de impresión 3d", and default title "l.fdo.cr". These are leftovers from a previous project and don't affect security, but undermine professional credibility.

INFO Hosted instance runs Plausible tracker

The layout includes <script defer data-domain="fdo.cr" src="/dolan/wat/script.js"> in production. This is a self-proxied Plausible snippet tracking visitors to the dashboard itself. For a product that markets "no third-party trackers," this warrants disclosure — even though Plausible is privacy-respecting, it's still a tracker on the authenticated app pages.

Analytics Trustworthiness

How much should an end user trust the numbers ugo shows them?

What makes the data reliable

  • First-party, server-side tracking. Every request to /:slug is recorded regardless of client-side JS, ad blockers, or browser privacy features. This is more reliable than client-side analytics.
  • Bot filtering. CrawlerDetect runs on every visit before it reaches the dashboard. Known bots are discarded.
  • No sampling. Every visit is recorded and processed. There's no statistical sampling that could introduce error.
  • Workspace RBAC. Analytics are scoped to workspace membership. No data leaks across tenants.
  • Cache invalidation. Chart cache keys are purged when new visits are processed, so data freshness is bounded by the 10-second processing interval.

What undermines the data

  • No click fraud protection. Anyone can curl /:slug in a loop and inflate numbers. There's no IP-based dedup, no CAPTCHA, no velocity check.
  • Unique visitor overcounting. Daily hash rotation means a 7-day "unique visitors" count is really "sum of daily uniques" — the same person is counted once per day.
  • "Unique visitors" displayed without caveat. The dashboard shows "Unique Visitors" as a stat without explaining the daily-rotation limitation.
  • GeoIP inaccuracy. MaxMind GeoLite2 is ~65-80% accurate at city level. VPN users show exit-node locations. This is inherent to all GeoIP, but users may not realize it.
  • No referrer spam detection. Fake referrers are stored and displayed as-is.
  • 60-minute chart cache. Although cache is invalidated on processing, the expires_in: 60.minutes fallback means stale data can persist if cache invalidation fails.
VERDICT: Analytics are directionally accurate and better than most client-side alternatives, but vulnerable to intentional manipulation.

Data Retention & Lifecycle

How long visit data lives, and what happens when it's deleted.

CleanupVisitsJob (runs monthly at 03:00 UTC) → Free workspaces: delete visits older than 1 month → Basic/Growth: delete visits older than 3 months → Dedicated/Self-hosted: no automatic cleanup (unlimited retention)

Assessment

Good

  • Retention limits exist and are enforced by a recurring job.
  • User account deletion cascades: User → owned_workspaces (destroy) → links (destroy) → visits (destroy).
  • Link deletion cascades visits via dependent: :destroy.
  • The privacy policy correctly states "You can delete your links and their associated analytics at any time."

Concerns

  • Raw IP persists for the full retention window. On paid plans, that's 3 months of IP addresses. On dedicated/self-hosted, it's forever.
  • No GDPR right-to-erasure mechanism for link clickers. A person who clicked a link has no way to request deletion of their visit data. The privacy policy offers erasure for account holders, not for visitors whose clicks were tracked.
  • SQLite delete_all doesn't VACUUM. Deleted visit data may persist on disk in SQLite's free pages until the next VACUUM or page reuse.

Redirect Page Security

The link.html.erb template is the public-facing redirect page. It has the widest attack surface.

How the redirect works

The page uses a JS redirect: window.location.href = "<%= raw j(@link.url) %>" and also provides an <a href> fallback and a <link rel="canonical">, both using raw @link.url.

The j() helper escapes JS string delimiters. The Link model validates URL scheme against ALLOWED_URL_SCHEMES = %w[http https].

Assessment

LOW The defense-in-depth is reasonable. The url_scheme_is_allowed validation blocks javascript:, data:, and vbscript: schemes. The j() helper prevents breaking out of the JS string context.

INFO The raw usage in the href and canonical attributes relies entirely on the model validation. If a URL containing double-quotes or angle brackets were to slip through URI.regexp validation, it could break out of the attribute. This is unlikely but fragile — using ERB::Util.html_escape on the URL in HTML attribute contexts would be strictly safer.

Social tag injection surface

Social tag fields (title, description, image_url) are rendered in <meta> tags without explicit escaping. ERB's default <%= auto-escapes HTML, so this is safe unless raw or html_safe is used. Confirmed: the social tag rendering uses <%=, so it is properly escaped.

SWOT Analysis

Strategic assessment of ugo as an analytics-bearing product.

Strengths

  • Privacy-first architecture. Daily-rotated hashes, no cookies on clicks, no third-party trackers on the redirect path. This is a genuine differentiator.
  • Open source & self-hostable. Full data sovereignty for self-hosted users. The O'Saasy license and Once deployment make this accessible.
  • Server-side tracking. Immune to ad blockers and browser privacy features that break client-side analytics. More accurate than JS-based competitors.
  • Simple, auditable codebase. Single Rails app, SQLite, no microservices. Easy to reason about, easy to audit, easy to deploy.
  • Solid Queue architecture. Deferred visit recording keeps the redirect fast. Separate SQLite DB for the queue is a smart isolation choice.
  • Good bot filtering. CrawlerDetect integration removes known bots before they hit dashboards.
  • Encrypted secrets at rest. SMTP creds, API keys, and setup codes use Active Record Encryption.

Weaknesses

  • Raw IP storage contradicts privacy positioning. The marketing says "respects you" but the DB stores raw IPs for weeks/months. This is the single biggest gap between promise and implementation.
  • No CSP. A fundamental web security header is entirely absent. This is table-stakes for any production SaaS.
  • No rate limiting on the redirect path. Analytics are trivially inflatable. This undermines trust in the numbers.
  • Unique visitor metric is misleading. Weekly/monthly "unique" counts are actually sums-of-daily-uniques due to hash rotation. Users may make decisions based on inflated uniqueness numbers.
  • Short data retention on paid plans. 3 months is short compared to competitors. No way to extend it.
  • No API for analytics data. Users can see charts but can't export or programmatically access their analytics. Lock-in by limitation.
  • Permanent session cookies. No expiry, no rotation. A stolen cookie is a permanent skeleton key.
  • Layout contains stale placeholder text from a previous project (Spanish meta tags, wrong title). Erodes trust on first inspection.

Opportunities

  • IP-after-processing nullification. A single migration + 1-line code change would make ugo's privacy story genuinely best-in-class, not just good.
  • CSP + Rack::Attack. Adding these two defenses would close the most critical security gaps and is straightforward in Rails.
  • Click fraud detection. IP-based velocity limiting (e.g., max N visits per IP per hour per link, enforced at recording time) would dramatically improve analytics trust.
  • Analytics API & CSV export. An API for analytics data would unlock integrations and reduce churn risk.
  • Privacy certification. With IP nullification and CSP, ugo could credibly pursue GDPR compliance certification, which would be a strong sales differentiator in EU markets.
  • UTM parameter capture. The URL builder adds UTM params to destination URLs, but ugo doesn't capture them from the redirect. Parsing UTMs from the destination URL and storing them as visit metadata would make the analytics much richer.
  • Longer retention tiers. A 12-month retention option for Growth/Dedicated would match market expectations.

Threats

  • GDPR enforcement. Storing raw IPs of EU visitors without explicit consent or legitimate interest documentation is a regulatory risk. A single complaint to a DPA could trigger scrutiny.
  • Click fraud at scale. Without rate limiting, a disgruntled competitor or troll can render any user's analytics meaningless. This is an existential threat to the product's value proposition.
  • Admin account compromise. The admin_scripts feature turns a single compromised admin into a stored XSS affecting every user on the instance. On the hosted ugo.cr service, this is a multi-tenant risk.
  • MaxMind license changes. GeoLite2 is free but requires a license key and compliance with MaxMind's EULA. License terms have changed before (2019). Dependency on a single geo provider is a supply-chain risk.
  • Competitive pressure. Dub.co, Short.io, and Bitly offer richer analytics (conversion tracking, A/B testing, advanced fraud detection). ugo's simplicity is a strength but the feature gap is real.
  • SQLite scaling ceiling. Single-writer SQLite works beautifully for small-to-medium traffic but will hit contention limits for high-volume dedicated instances.

End-User Trust Assessment

What should a user of ugo.cr (or a self-hosted instance) expect?

For link creators (dashboard users)

  • Your analytics are directionally accurate for organic traffic.
  • Unique visitor counts are daily estimates, not precise. Expect overcounting on weekly/monthly views.
  • Your data is workspace-isolated and only visible to team members.
  • Your data is deleted after 1-3 months depending on plan.
  • Risk: Anyone with your short URL can inflate your click counts with no mitigation.

For link clickers (end visitors)

  • No cookies are set on you. No cross-site tracking.
  • Your IP address is stored in the database for 1-3 months.
  • Your approximate lat/lng is derived and stored.
  • Your full user-agent string is stored.
  • You have no mechanism to request deletion of your click data.
  • On self-hosted instances: the operator controls retention and may keep data indefinitely.

For self-hosted operators

  • You have full data sovereignty. No data leaves your server.
  • Encryption keys are auto-generated and stored locally.
  • No cleanup job runs by default for dedicated plans — data grows unbounded.
  • You are the GDPR data controller.
  • Risk: If you enable admin_scripts, you accept the XSS surface that entails.

Priority Action Items

Ranked by impact-to-effort ratio. The top 5 would dramatically improve the product's security and privacy posture.

1. HIGH Nullify IP address after processing

In ProcessVisitsJob, after GeoIP lookup and visitor hash are computed, set ip_address to nil. Make the column nullable. Effort: ~30 minutes. Transforms the privacy story from "we store your IP" to "we transiently use your IP and discard it."

2. HIGH Enable Content Security Policy

Uncomment and configure the CSP initializer. Start with report-only mode, then enforce. This is the single most impactful security improvement. Effort: ~1 hour.

3. MED Add rate limiting to redirect endpoint

Add rate_limit to: 30, within: 1.minute on LinksController#link (scoped by IP), or add Rack::Attack middleware. Effort: ~1 hour. Prevents trivial analytics inflation.

4. MED Use secure_compare for API key auth

Replace @api_key == AppConfig.shared.admin_api_key with ActiveSupport::SecurityUtils.secure_compare. Effort: 5 minutes.

5. MED Add session expiry

Replace cookies.signed.permanent with a bounded expiry (e.g., 30 days). Add a last_active_at check on session resume. Effort: ~30 minutes.

6. LOW Fix layout meta tags

Replace the stale Spanish placeholder meta tags, fix lang="es" to lang="en", and set the default title to the app name. Effort: 5 minutes.

Final Verdict

Overall assessment across three dimensions.

Analytics Trust

GOOD WITH CAVEATS

Server-side tracking is inherently more reliable than client-side. Bot filtering is solid. But the lack of click fraud protection and the misleading "unique visitors" metric on multi-day ranges are real trust gaps.

Security Posture

NEEDS WORK

The foundation is sound (force_ssl, encrypted secrets, CSRF, auth). But the absent CSP, unguarded admin_scripts injection, permanent sessions, and no rate limiting on the hottest endpoint are gaps that a production SaaS shouldn't ship with.

Privacy

RAW IP MUST GO

The visitor hash design is excellent and shows real intent. But storing the raw IP alongside it negates the privacy benefit. Fix this one thing and the privacy story goes from "mixed" to "best-in-class among URL shorteners."

Bottom line: ugo has a strong architectural foundation and a genuine privacy-first intent that most competitors lack. The issues found are all fixable with modest effort. The top 3 action items (IP nullification, CSP, rate limiting) could be shipped in a single afternoon and would meaningfully de-risk the product for both hosted and self-hosted users.
